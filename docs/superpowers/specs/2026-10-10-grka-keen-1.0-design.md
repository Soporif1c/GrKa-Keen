# GrKa Keen 1.0 — спецификация

Дата: 2026-10-10. Статус: на согласовании.
Макет интерфейса: https://claude.ai/artifact/1kXXVWqxERmFzZLWFFzpjX

## 1. Цель

Превратить GrKa Keen 0.0.2 (панель mihomo для Keenetic) в надёжную панель с двумя ядрами (Xray и mihomo), понятным выбором «какой сервис через VPN» и отдельной обработкой игровых устройств.

Критерии готовности:

1. После перезагрузки роутера, переподключения провайдера и перестройки файрвола правила восстанавливаются сами, без нажатий в панели.
2. Экран «Сервисы» позволяет переключить любой сервис или игровую платформу между «Напрямую» и «VPN» и применить изменения одной кнопкой.
3. Игровые устройства получают открытый NAT: их игровой трафик идёт мимо ядра.
4. DoT/DoH, настроенные на роутере, остаются единственным путём DNS наружу. Открытый DNS не уходит в интернет ни от клиентов, ни от ядра.
5. Работают оба ядра. Xray ставится любой версии, включая pre-release, и совпадает по протоколам с нодами GrKa VPN (сейчас на нодах Xray 26.7.28).
6. Списки сервисов, игровых платформ и заблокированного в РФ обновляются без обновления панели.
7. Исправлены все ошибки из раздела 3.

Вне рамок 1.0: управление составом политики из панели (устройства добавляются в Keenetic), отдельные профили сервисов для разных групп устройств, графики трафика, удалённый доступ к панели из интернета.

## 2. Исходные условия

- Роутеры Keenetic с Entware: aarch64, mipsel, mips (основной стенд — Keenetic Ultra KN-1811, aarch64, KeeneticOS 5.1.7).
- Окружение: busybox ash, `jq`, `curl`, `ip-full`, `iptables`, `unzip`, `lighttpd` + `mod_cgi`. Бэкенд остаётся на shell + jq, без Python и Node на роутере.
- Политика доступа Keenetic маркирует пакеты своих клиентов fwmark. Метка видна через RCI `show/ip/policy`.
- На KeeneticOS 5.2 и новее локальный RCI (`127.0.0.1:79/rci`) требует токен в заголовке `X-Ndma-Tkn`.
- На GitHub все релизы Xray после v26.3.27 помечены pre-release. Запрос `/releases/latest` для Xray использовать нельзя.

## 4. Архитектура

```
Браузер ── HTTP :1100 ──► lighttpd ─► CGI api (sh + jq)
                                         │ читает/пишет
                                         ▼
              /opt/etc/grka: settings.json, state.json, servers.json, catalog/
                                         │ сигнал «применить»
                                         ▼
NDM-хуки ── флаг ──► сторож grka-watchdog ──► генератор (jq) ─► конфиг ядра
                        │                                         │
                        ├─ запуск/остановка ядра (Xray или mihomo) ◄┘
                        ├─ ip rule / таблицы маршрутов
                        ├─ iptables: перенаправление DNS игровых устройств
                        └─ статус-файл и журнал событий
```

Компоненты и их единственные обязанности:

- **CGI `api`** — принимает команды панели, проверяет их, сохраняет данные, ставит фоновые задачи. Сам маршруты не трогает.
- **Сторож** — единственный владелец жизненного цикла ядра и правил маршрутизации. Приводит систему к желаемому состоянию и пишет журнал.
- **Генератор** — чистые jq-программы: из `state.json`, `servers.json`, каталога и настроек делают конфиг Xray или mihomo. Без побочных эффектов, тестируются отдельно.
- **Адаптеры ядер** — `core-xray.sh` и `core-mihomo.sh` с одинаковым набором функций (§7.1).
- **Каталог** — данные о сервисах, собираются GitHub Action в репозитории, роутер их скачивает (§8.4).

## 5. Маршрутизация

### 5.1. Схема

Одна политика Keenetic (по умолчанию `GrKa`, имя настраивается). Устройства добавляются в неё в веб-интерфейсе Keenetic. В панели у каждого устройства политики есть тип: «Обычное» (по умолчанию) или «Игровое».

- **Обычные устройства:** весь трафик идёт в ядро, ядро решает по правилам.
- **Игровые устройства:** в ядро идёт только то, что должно уйти в VPN. Всё остальное маршрутизируется роутером как без VPN.

Устройство идентифицируется по MAC. Его текущий IPv4 сторож берёт из RCI `show/ip/hotspot`.

### 5.2. Правила `ip rule` и таблицы

Метка политики — `M`, TUN-устройство ядра — `grka-tun` (одно имя для обоих ядер).

| pref | Правило | Назначение |
|---|---|---|
| 96 | `fwmark M to <частная сеть> lookup main`, по одному на 10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10 | Локальные адреса не уходят в ядро |
| 97 | `from <IP игрового> fwmark M lookup 1002`, по одному на устройство | VPN-трафик игрового устройства идёт в ядро |
| 98 | `from <IP игрового> fwmark M lookup main`, по одному на устройство | Остальной трафик игрового устройства идёт мимо ядра |
| 99 | `fwmark M lookup 1001` | Весь трафик обычных устройств идёт в ядро |

- Таблица **1001**: `default dev grka-tun` и `unreachable default metric 4294967295`. Если ядро упало и TUN исчез, остаётся `unreachable`: у обычных устройств нет интернета, утечки мимо VPN нет.
- Таблица **1002**: `198.18.0.0/15 dev grka-tun` (диапазон fake-IP) и маршруты `dev grka-tun` для IP-списков сервисов, выставленных в «VPN» (например, Telegram). Если ядро упало, маршруты исчезают, и трафик игрового устройства уходит по pref 98 напрямую.
- **Режим «VPN на паузе»:** pref 99 указывает на `main`, правила pref 97–98 и перенаправление DNS снимаются. Ядро может продолжать работать.
- **Полная остановка** из панели снимает все правила. Дальше работает сама политика Keenetic. Рекомендация остаётся прежней: политике не назначать подключения, тогда без GrKa Keen у её клиентов нет интернета.
- Для `grka-tun` сторож выставляет `rp_filter=2`: эффективное значение — максимум из `all` и интерфейса, поэтому получится loose-режим. Если на роутере понадобится разрешение `FORWARD` для `grka-tun`, сторож его ставит (проверяется на стенде).

### 5.3. DNS

Принцип: наружу DNS уходит только через DoT/DoH роутера.

- **Обычные устройства:** DNS не перехватывается. Устройства спрашивают роутер, роутер идёт через DoT/DoH. Ядро определяет домен по самому соединению (sniffing TLS/HTTP/QUIC) и подставляет его в адрес назначения. Для VPN-трафика домен разрешает сервер, поэтому сайты отдают «заграничные» адреса, а не российские кэши.
- **Игровые устройства:** запросы на порт 53 от их IP (udp и tcp) перенаправляются iptables `REDIRECT` в DNS ядра на порт 1053. Ядро отвечает fake-IP только для доменов, которые должны идти в VPN. Остальные домены ядро разрешает через DNS роутера, то есть через тот же DoT/DoH. Если ядро не работает, сторож снимает перенаправление.
- **Собственные запросы ядра** (адреса VPN-серверов, прямые соединения) тоже идут через DNS роутера (`127.0.0.1:53`; если там не отвечает, адрес моста LAN).
- DNS-слушатель ядра привязан к адресу моста LAN, а не к `0.0.0.0`.
- Ограничение: игровое устройство со своим DoH/DoT обходит выбор «VPN» по доменам. Для приставок это редкость, в интерфейсе есть подсказка.
- На «Обзоре» показывается, включён ли на роутере шифрованный DNS (по данным RCI), с предупреждением, если нет.

### 5.4. Идемпотентность

Каждая функция «применить» сначала читает текущее состояние (`ip rule show`, `ip route show table N`, `iptables -S`), удаляет лишнее (правила наших pref с чужой меткой или чужими IP) и добавляет недостающее. Повторный запуск ничего не меняет. Все изменения iptables идут с `-w`.

### 5.5. IPv6

Для меченого трафика ставится `ip -6 rule add fwmark M prohibit pref 99`, и устройства политики переходят на IPv4. Ставит ли NDM метку на IPv6-пакеты, проверяется на стенде. Если нет, «Обзор» показывает предупреждение, когда на LAN включён IPv6.

## 6. Сторож

### 6.1. RCI-клиент

- `rci_get <path>`: `curl` к `127.0.0.1:79/rci/<path>`, с заголовком `X-Ndma-Tkn`, если токен задан в настройках.
- Коды 401/403 означают «нужен токен». Состояние попадает в статус, «Обзор» и «Настройки» показывают подсказку, где взять токен (Keenetic, раздел «Пользователи и доступ»).
- Последняя успешная метка политики кэшируется в `/opt/etc/grka/cache/policy_mark`. При загрузке, пока RCI не отвечает, используется кэш с пометкой в журнале.

### 6.2. Цикл

Сторож — фоновый процесс с PID-файлом, запускается из `S99grka-keen`. Шаг 1 секунда, полная проверка раз в 10 секунд или сразу при флаге `/tmp/grka/dirty`.

1. **Загрузка.** Ждать ответа RCI без ограничения по времени: повтор каждые 2 секунды первую минуту, потом каждые 10. Каждая попытка пишется в журнал раз в минуту.
2. **Желаемое состояние:** включено ли ядро, пауза, метка политики, IP игровых устройств, тип ядра, путь к конфигу.
3. **Ядро.** Если оно должно работать, но не работает, запуск. Паузы между перезапусками: 5 с, 15 с, 60 с. После трёх неудач за 5 минут попытки прекращаются, состояние «ошибка» с последними строками лога ядра. Новая попытка — после изменения конфига или по кнопке.
4. **TUN.** Ждать `grka-tun` до 30 секунд после старта ядра.
5. **Правила.** Применить §5.2 и §5.3 идемпотентно.
6. **RCI обновляется** раз в 60 секунд: метка, хосты политики, IP игровых устройств. Изменение IP вызывает перестройку правил pref 97–98 и цепочки DNS.
7. **Статус** пишется в `/tmp/grka/status.json` атомарно (запись во временный файл и `mv`).
8. **Журнал.** Пишутся только изменения и ремонты, например «Роутер пересобрал правила файрвола. Перенаправление DNS восстановлено». Повторяющееся событие не пишется чаще раза в минуту.

### 6.3. Хуки NDM

`netfilter.d/50-grka.sh` и `ifstatechanged.d/50-grka.sh` только создают `/tmp/grka/dirty` и завершаются. Гонок нет: правила меняет один процесс.

### 6.4. Команда `grka`

Для SSH: `grka status`, `grka apply`, `grka pause`, `grka resume`, `grka logs`, `grka diag`. Последняя собирает в архив всё нужное для разбора проблемы (без токенов и ссылок подписки).

## 7. Ядра

### 7.1. Интерфейс адаптера

Каждый адаптер (`lib/core-xray.sh`, `lib/core-mihomo.sh`) реализует:

`core_installed`, `core_version`, `core_bin`, `core_list_versions`, `core_install <версия>`, `core_rollback`, `core_validate <файл>`, `core_start`, `core_stop`, `core_reload`, `core_latency <сервер>`.

Сторож и CGI обращаются только к этим функциям.

### 7.2. Запуск

- Ядро запускается от сторожа и пишет PID-файл. Остановка идёт по PID, а не через `killall`.
- Xray: `xray run -confdir` с `XRAY_LOCATION_ASSET=/opt/etc/grka/catalog/geo`.
- mihomo: `mihomo -d <каталог> -f <конфиг>`.
- Переключение ядра: остановить текущее, сгенерировать конфиг для другого, проверить, запустить. Если не вышло, вернуть прежнее.

### 7.3. Применение изменений

Генерация в `config.new`, затем `core_validate` (`xray run -test`, `mihomo -t`), затем атомарная замена. Перезагрузка: у mihomo через API `PUT /configs?force=true`, у Xray перезапуск. Если проверка не прошла, рабочий конфиг не меняется, а панель показывает вывод ядра.

### 7.4. Версии и обновление

- Список версий: GitHub API `/releases?per_page=30` с pre-release, кэш на час. У каждой версии метка «стабильная» или «pre-release».
- Можно закрепить версию. Тогда «Обновить» её не меняет.
- Xray: архив `Xray-linux-<arch>.zip` (распаковка `unzip`), проверка SHA256 из `.dgst`. Соответствие архитектур: aarch64 → `arm64-v8a`, armv7 → `arm32-v7a`, mipsel → `mips32le`, mips → `mips32`, x64 → `64`.
- mihomo: как сейчас, архитектура определяется по `opkg print-architecture`.
- Предыдущая версия бинарника хранится для отката. Компактный режим (сжатый бинарник в `/opt`, распаковка в RAM) работает для обоих ядер.
- Минимальная поддерживаемая версия Xray — 26.3.27, проверяется при установке.

### 7.5. Режим эксперта

Для каждого ядра можно включить свой конфиг вместо сгенерированного. Сторож по-прежнему управляет маршрутизацией и DNS, но конфиг берётся из `expert/`. В нём обязательны TUN `grka-tun` без автомаршрутов и DNS-слушатель на 1053, если есть игровые устройства. Это проверяется перед применением. Экран «Сервисы» в этом режиме показывает баннер. Если в своём конфиге mihomo пустой `secret` или API слушает `0.0.0.0`, «Обзор» предупреждает об этом и предлагает исправить одной кнопкой.

## 8. Сервисы, серверы, каталог

### 8.1. Данные пользователя — `state.json`

```json
{
  "schema": 1,
  "core": "xray",
  "rest": "direct",
  "main_server": "auto",
  "services": { "youtube": { "route": "vpn", "server": "main" }, "steam": { "route": "direct" } },
  "games_other_direct": true,
  "ads_block": true,
  "quic_block_vpn": true,
  "rules": [ { "match": "example.com", "route": "vpn" } ],
  "devices": { "AA:BB:CC:DD:EE:FF": { "type": "gaming" } },
  "paused": false
}
```

Для сервисов, которых нет в `services`, берётся значение по умолчанию из каталога. Сервис, исчезнувший из каталога, игнорируется. Его запись остаётся на случай возврата.

### 8.2. Порядок правил

Сверху вниз, первое совпадение побеждает:

1. Служебные: DNS-запросы в DNS ядра, частные адреса напрямую, BitTorrent напрямую (ноды GrKa VPN его блокируют).
2. Свои правила пользователя, по порядку.
3. Реклама — блок, если включено.
4. Конкретные сервисы и игровые платформы, в порядке каталога.
5. «Заблокированное в РФ».
6. «Российские сервисы».
7. «Прочий игровой трафик напрямую», если включено: UDP на порты кроме 53, 123 и 443.
8. Остальной трафик: напрямую или VPN.

Если включён `quic_block_vpn`, перед каждым правилом с маршрутом «VPN» ставится такое же правило для UDP 443 с маршрутом «блок». Браузер тогда переходит на TCP, который через VLESS работает стабильнее.

Маршрут «VPN» указывает на сервер сервиса, если он задан, иначе на основной сервер. «Самый быстрый»: у Xray балансировщик `leastPing` с `observatory` по всем серверам, у mihomo группа `url-test`.

### 8.3. Серверы — `servers.json`

- **Подписка** (одна или несколько ссылок):
  - Xray: панель запрашивает `<ссылка>/json` у Remnawave. Из каждого конфига массива берётся outbound `proxy` целиком, поэтому finalmask, XHTTP и прочие настройки сохраняются. Название сервера — `remarks`.
  - mihomo: подписка идёт в конфиг как `proxy-providers` с `<ссылка>/mihomo`, mihomo скачивает её сам.
  - Если ответ не в ожидаемом формате, запасной вариант — список ссылок без суффикса.
  - Обновление раз в сутки и по кнопке. User-Agent: `GrKa-Keen/<версия>`.
- **Ссылки:** `vless`, `vmess`, `trojan`, `ss` (с плагинами), `hysteria2`/`hy2` (с `mport`), `tuic`. Поддерживаются REALITY с `spx`, XHTTP, VLESS encryption. Разбор — одна реализация на jq (`lib/parse-link.jq`). Из ссылки получается outbound Xray и proxy mihomo.
- **Пинг:**
  - mihomo: Clash API `/proxies/<имя>/delay`.
  - Xray: в конфиг добавляется по socks-входу на `127.0.0.1:20800+N` для каждого сервера. CGI замеряет `curl` через этот вход время до `https://www.gstatic.com/generate_204`.

### 8.4. Каталог

**Источник** — папка `catalog/` в репозитории GrKa-Keen: `catalog.json` с категориями и сервисами, исходные списки, иконки.

```json
{
  "id": "youtube", "title": "YouTube", "desc": "YouTube, YouTube Music, Shorts",
  "category": "video", "icon": "youtube.svg", "default": "vpn",
  "match": { "geosite": ["youtube"], "geoip": [], "domains": [], "cidr": [], "asn": [] }
}
```

**Сборка** — GitHub Action по расписанию (каждые 6 часов) и при изменении каталога:

- Берёт нужные категории из runetfreedom/russia-v2ray-rules-dat (`ru-blocked`, `ru-available-only-inside`, `category-ads-all`) и v2fly domain-list-community (остальные).
- Собирает IP-списки игровых платформ по ASN через RIPEstat. Пример: Valve AS32590, Riot AS6507, Blizzard AS57976. Остальные ASN уточняются при сборке.
- Делает облегчённые `geosite.dat` и `geoip.dat` только с категориями каталога для Xray. Полный `geosite.dat` runetfreedom весит 70 МБ, для роутера это не подходит.
- Делает `.mrs` по каждой категории для mihomo (`mihomo convert-ruleset`).
- Пишет `manifest.json` с версией и SHA256 всех файлов.
- Публикует всё в ветку `catalog` (+ purge кэша jsDelivr).

**Обновление на роутере** (`catalog-update.sh`, раз в сутки и по кнопке):

- Скачивает `manifest.json`, затем изменившиеся файлы. Проверяет SHA256 и меняет файлы атомарно, затем запускает «применить».
- Источники по порядку: jsDelivr, raw.githubusercontent, через локальный socks ядра (если VPN работает).
- В пакете панели лежит встроенный каталог на случай, если скачать не удалось.

## 10. CGI API

Запрос: `POST /cgi-bin/api` с JSON `{"method": "...", "params": {...}}`. Ответ: `{"ok": true, ...}` или `{"ok": false, "error": "текст для человека", "code": "машинный_код"}`.

| Группа | Методы |
|---|---|
| Состояние | `status` (содержимое `status.json`), `journal` |
| Сервисы | `state.get`, `state.set` (проверка схемы, запись, применение) |
| Каталог | `catalog.get`, `catalog.update` |
| Серверы | `servers.get`, `servers.add_link`, `servers.remove`, `subscription.set`, `subscription.refresh`, `servers.latency` |
| Устройства | `devices.get` (хосты политики из RCI и их типы), `devices.set_type` |
| Ядро | `core.get`, `core.versions`, `core.install`, `core.switch`, `core.rollback`, `core.pin` |
| Эксперт | `expert.get`, `expert.set`, `expert.validate` |
| Сервис | `service.pause`, `service.resume`, `service.restart` |
| Настройки | `settings.get`, `settings.set` |
| Журналы | `logs.core` |
| Задачи | `task.status` (долгие операции идут фоном, лог задачи в `/tmp/grka/task.log`) |

`status` не делает RCI-запросов и не запускает скриптов: он отдаёт файл сторожа.

## 11. Хранение

```
/opt/share/grka/            код: www/, bin/ (grka, grka-watchdog), lib/ (*.sh, *.jq), catalog/ (встроенный), version
/opt/etc/grka/settings.json настройки панели: имя политики, токен, порт, хэш пароля, автозапуск, компактный режим, уровень лога, закреплённые версии
/opt/etc/grka/state.json    выборы пользователя (§8.1)
/opt/etc/grka/servers.json  серверы и подписки
/opt/etc/grka/catalog/      скачанный каталог: catalog.json, geo/, mrs/, ip/, icons/
/opt/etc/grka/cores/<ядро>/ бинарник, предыдущая версия, сгенерированный конфиг
/opt/etc/grka/expert/       свои конфиги
/opt/etc/grka/backups/      копии state, servers и конфигов, последние 10
/opt/var/log/grka/journal.log  журнал сторожа (только события, ротация 256 КБ)
/tmp/grka/                  core.log, status.json, dirty, PID-файлы, задачи
/opt/etc/init.d/S99grka-keen   панель и сторож
```

- Все JSON-файлы пишутся через jq во временный файл и `mv`.
- `lighttpd.conf` панели генерируется из `settings.json` при каждом запуске `S99grka-keen` (порт, адрес). Поэтому смена порта переживает обновления.
- Обновление панели (архив или ipk) не трогает `/opt/etc/grka`.
- Init-скрипты не помечаются как conffiles, это код.

## 12. Безопасность

- **CSRF:** CGI принимает только `Content-Type: application/json` и заголовок `X-GrKa-Request: 1`. Если в запросе есть `Origin`, он должен совпадать с `Host`. Иначе 403.
- **Пароль панели** (по желанию): соль и SHA-256 в настройках. Сессия — случайный токен в cookie `HttpOnly; SameSite=Strict`.
- **mihomo API:** случайный `secret` при генерации. Панель получает его со своего origin. Слушает адрес моста LAN, а не `0.0.0.0`.
- **Входы ядер:** socks и mixed только на `127.0.0.1`, DNS на адресе моста LAN.
- **Секреты в выводе:** токен RCI и ссылки подписок не показываются целиком, не попадают в журнал и в `grka diag`.
- **Ввод:** имена файлов и параметры проверяются (нет `/`, `..`, управляющих символов). Все данные идут через jq, без подстановки в shell-команды.

## 13. Логи

- **Лог ядра:** `/tmp/grka/core.log` в RAM, ротация при 1 МБ, одна старая копия. Уровень по умолчанию `warning`. Режим «подробно» включается кнопкой на 30 минут.
- **Журнал сторожа:** короткие события на русском, хранится на флеше, мало записей.

## 14. Переход с 0.0.2

Новый пакет сохраняет имя `S99grka-keen`: самообновление 0.0.2 перезапускает именно его. При первом старте 1.0 разово выполняется `migrate.sh`:

1. Останавливает mihomo, запущенный старым `S97mihomo`. Сам `S97mihomo` переименовывает в `S97mihomo.grka-disabled`.
2. Переносит `POLICY_NAME` из `grka.conf` в `settings.json`.
3. Ставит `core=mihomo` и режим эксперта с текущим `/opt/etc/mihomo/config.yaml`. Поведение не меняется.
4. Старые хуки NDM заменяются новыми с теми же именами.
5. Пишет отметку о миграции. Мастер предложит перейти на сгенерированные правила и Xray.

Без миграции 0.0.2 и новый сторож запустили бы два ядра одновременно.

## 15. Проверка

- **Генератор (jq):** набор входных `state`/`servers`/`catalog` и ожидаемых выходов. Каждый сгенерированный конфиг проверяется настоящими `xray run -test` и `mihomo -t` (Windows-сборки последних версий на машине разработки).
- **Парсер ссылок:** таблица ссылок, включая ваши форматы (VLESS TLS Vision, REALITY, XHTTP, Hysteria2), и ожидаемых outbound/proxy.
- **Shell:** `shellcheck` в режиме sh. Логика сторожа и правил тестируется в busybox ash с заглушками `ip`, `iptables`, `curl` (RCI), которые записывают вызовы. Проверяются сценарии: загрузка с недоступным RCI, смена метки, смена IP игрового устройства, исчезновение TUN, перестройка netfilter, падение ядра и паузы между перезапусками.
- **Интерфейс:** демо-режим, ручная проверка экранов на ширинах 1360 и 390.
- **Стенд (KN-1811, по чек-листу пользователя):**
  - три перезагрузки подряд;
  - переподключение WAN;
  - смена IP игрового устройства;
  - `kill -9` ядра;
  - переключение ядра;
  - обновление каталога;
  - проверка, что DNS уходит только через DoT/DoH (счётчики пакетов на 53 и 853 порту WAN);
  - проверка NAT на приставке.

## 16. Этапы

Каждый этап проверяется отдельно и получает свой план.

1. **Фундамент:** настройки, CSRF, RCI-клиент, сторож, правила §5, новые хуки, логи, `grka`, миграция. Работает с текущим конфигом mihomo в режиме эксперта.
2. **Ядра:** адаптеры, установка с выбором версии, проверка, откат, компактный режим, переключение.
3. **Генератор и серверы:** `state.json`, генераторы Xray и mihomo, парсер ссылок, подписки, пинг.
4. **Каталог:** структура `catalog/`, GitHub Action, `catalog-update.sh`, встроенный каталог.
5. **Интерфейс:** все экраны, мастер, режим эксперта, демо-режим.
6. **Выпуск:** сборка tar и ipk, README, 1.0.0-beta.1, проверка на стенде, исправления, 1.0.0.
